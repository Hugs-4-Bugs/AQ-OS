# ACQUISITIONOS — MASTER LEAD DISCOVERY, ENRICHMENT & BULK EXPORT IMPLEMENTATION

## 0. PROJECT AUTHORITY AND OBJECTIVE

You are working on AcquisitionOS, an existing SaaS application for discovering, analyzing, qualifying, and managing business acquisition and customer acquisition opportunities.

**Authoritative repository:**
https://github.com/Hugs-4-Bugs/AQ-OS

**Authoritative branch:** `main`

Use the current state of this repository as the reference for the application's existing implementation.

Your task is to audit, repair, and improve the existing lead discovery system so it reliably discovers substantial numbers of relevant leads across supported sources, analyzes their business and website quality, enriches their details, categorizes them, and supports bulk export according to the user's subscription plan.

The current implementation sometimes:

* Returns only 2, 4, 6, 10, or 12 leads when users expect bulk results.
* Fails to discover leads despite having valid search criteria.
* Displays "No suitable leads found" without adequately explaining the reason.
* Fails to discover relevant businesses with missing, broken, outdated, or poor-quality websites.
* Does not consistently provide complete, verified, enriched lead information.
* Has limited country options instead of worldwide search.
* Does not provide a sufficiently reliable bulk discovery and export experience.

**Fix the underlying problems. Do not merely increase a displayed result count or change the UI while the backend still returns insufficient data.**

The objective is a reliable, scalable, plan-aware lead acquisition system that delivers useful, evidence-backed business prospects rather than generic company lists that users could obtain from a basic ChatGPT or Gemini prompt.

# 3. BULK LEAD DISCOVERY ENGINE

## 3.1 Core behavior

Users must be able to discover leads in bulk based on:

* Business niche and industry.
* Search keywords and phrases.
* Country.
* State, province, or region.
* City.
* Postal code, where supported.
* Specific location or geographic radius, where supported.
* Business type.
* Website status and quality.
* Additional existing filters supported by AcquisitionOS.

The system should retrieve as many relevant, distinct leads as it can reasonably obtain from the selected sources, within the user's plan limits, provider quotas, legal restrictions, and available resources.

Do not hardcode a tiny global result limit such as 10 or 12 when the provider and user's plan permit more results.

Do not remove legitimate limits imposed by a provider or subscription plan.

## 3.2 Pagination and batch processing

Implement or repair the existing pagination and batch-processing mechanisms.

* Retrieve subsequent pages when the provider supports pagination.
* Continue discovery until the target is reached, the provider is exhausted, the user cancels, or a genuine quota/resource limit is reached.
* Respect provider pagination tokens and continuation cursors.
* Support bounded concurrent requests where appropriate.
* Use configurable batch sizes and concurrency limits.
* Prevent duplicate requests and uncontrolled parallel execution.
* Handle provider rate limits with appropriate backoff.
* Preserve completed results if a later batch fails.
* Support safe retry of failed batches without duplicating saved leads.
* Show actual progress: discovered, processed, rejected, saved, and remaining where known.
* Allow long-running jobs to complete without requiring the browser to remain continuously active, where compatible with the existing architecture.
* Support cancellation without corrupting completed results.

Do not simulate progress or report requested result counts as actual discovered results.

## 3.3 Search expansion

When the initial query returns few results, intelligently expand discovery using relevant query variants.

Examples:

* Industry synonyms.
* Business-category alternatives.
* Local-language keywords where supported.
* Relevant service and product terms.
* City, region, and nearby geographic variations.
* Relevant commercial phrases.

Query expansion must preserve the user's actual intent.

Do not broaden a narrowly defined search into unrelated industries merely to increase the count.

Record which query or search variation produced each lead where feasible.

## 3.4 No-result behavior

Do not immediately display "No suitable leads found" simply because one source or one query returned zero results.

Before returning a final no-results state:

1. Check whether the source request actually succeeded.
2. Distinguish an empty result from a failed request.
3. Check pagination and continuation behavior.
4. Check whether the query and location were passed correctly.
5. Run relevant query expansions when appropriate.
6. Try other sources only when the user selected them or explicitly enabled multi-source discovery.
7. Deduplicate and qualify any additional results.

If no results are available, explain the actual reason where known:

* No matching businesses found.
* Provider returned no results.
* API credentials are missing.
* Provider quota has been reached.
* Provider is temporarily unavailable.
* Search filters are too restrictive.
* Results were rejected by qualification rules.

Provide actionable suggestions without inventing leads.

# 6. WEBSITE PRESENCE AND QUALITY ANALYSIS

A key AcquisitionOS use case is identifying businesses that may need a better website or a new website.

The system must identify and categorize businesses with:

* No website found.
* Website URL present but unreachable.
* Broken or invalid website.
* HTTPS/TLS problems.
* Persistent server errors.
* Redirect loops or excessive redirects.
* Domain or DNS resolution failures.
* Very slow responses.
* Mobile usability concerns, when measurable.
* Outdated or incomplete website content, where reliable evidence is available.
* Missing basic business information.
* Weak online presence despite an otherwise relevant business.

## 6.1 Website checks

Use safe, bounded checks:

* Normalize and validate URLs.
* Resolve redirects safely.
* Record HTTP status where available.
* Check HTTPS and certificate errors.
* Measure response time.
* Distinguish a genuine failure from a temporary network error.
* Handle blocked requests, bot protection, timeouts, and unavailable pages.
* Avoid repeated checks that overload a target website.
* Prevent SSRF and requests to private, loopback, link-local, or otherwise prohibited network addresses.
* Revalidate resolved destinations after redirects to prevent SSRF bypasses.
* Use bounded timeouts, response sizes, and concurrency.
* Do not execute arbitrary website JavaScript or download unrestricted content.

## 6.2 Website quality classification

Create transparent, evidence-based classifications such as:

* No Website Found.
* Website Unreachable.
* Website Health Issue.
* Potential Improvement Opportunity.
* Website Appears Functional.
* Not Yet Verified.

Do not classify a website as "bad" or "outdated" based solely on a missing response or a failed automated request.

For subjective assessments, record the observable reasons and label them as estimates.

Do not claim mobile responsiveness, accessibility, SEO quality, or visual quality has been verified unless the relevant checks were actually performed.

## 6.3 Opportunity relevance

Prioritize businesses whose website status and business category match the user's target.

For example, if the user searches for dental clinics in a particular city, relevant results should include dental clinics in that location, with website issues clearly identified.

Do not rank unrelated businesses higher simply because they have no website.

## 7.1 Field-level correctness

Treat each field independently.

A verified business name does not automatically make its email, phone number, address, or website verified.

Normalize phone numbers and email addresses where possible, but do not alter the underlying evidence.

Use authoritative evidence and independent corroboration where available.

For uncertain fields, retain the value only with an appropriate status and source.

## 7.2 Verification labels

At minimum, support:

* Verified.
* Partially Verified.
* Unverified.
* Verification Failed.
* Conflicting Information.

Define explicit verification rules for each field.

Examples:

* A website URL was found in a business listing: URL discovered, not necessarily verified as the official site.
* A website returned a successful response: reachable at the check time, not necessarily owned by the business.
* A phone number appears in one listing: discovered, not necessarily confirmed.
* A business is present in two independent sources: corroborated identity, not proof that every field is correct.

Never use the word "verified" as a blanket claim without a documented basis.
