# AcquisitionOS — Complete Admin Dashboard

## Full Functional, Operational, Analytics & Security Requirements

Build a **fully functional, production-ready Admin Dashboard for AcquisitionOS**.

This is a complete product requirement. Do not create a mock dashboard, static dashboard, demo data dashboard, or UI-only dashboard.

The Admin Dashboard must use the **real AcquisitionOS data, real application events, real payment records, real users, real subscriptions, real credits, real leads, real workflows, real system metrics, real errors, and real feedback data** available in the application.

Before implementation, inspect the complete current codebase, existing database schema, authentication system, subscription system, payment integrations, credit system, workflows, lead system, AI usage, feedback system, API architecture, logging, cron/jobs, monitoring, and existing admin/security capabilities.

Do not invent duplicate systems when an existing production capability already exists. Extend and integrate with the existing architecture wherever appropriate.

---

# 1. ADMIN ACCESS & SECURITY

The Admin Dashboard must be a privileged application area and must be treated as highly sensitive.

## Authentication

Admin access must require authenticated identity.

Admin access must never be granted merely because a user knows or visits the admin URL.

Admin authentication must be strongly protected and must use the application's canonical authentication/session system.

Admin sessions must be securely validated.

Administrative access must be denied by default.

Unauthenticated users must have zero access to:

* Admin pages
* Admin APIs
* Admin analytics
* User data
* Payment data
* System logs
* Audit logs
* Internal metrics
* Sensitive configuration
* Administrative actions

## Role-Based Access Control

Implement proper RBAC for administrative functionality.

The system must support clearly defined administrative roles/permissions appropriate for the application.

At minimum, the architecture must support separation between:

* Super Admin
* Admin
* Support/Operations
* Analytics/Read-only
* Other restricted administrative roles if required by the existing application

Do not give every administrative user unrestricted access.

Permissions must be granular enough to control:

* User viewing
* User modification
* User deletion
* User banning
* Impersonation
* Credit adjustments
* Plan changes
* Payment visibility
* Refund visibility
* Revenue analytics
* System health
* Logs
* Audit logs
* Feedback management
* Security configuration
* Administrative settings

Sensitive operations must require explicit authorization.

## Server-Side Authorization

Security must never depend only on hiding UI elements.

Every Admin API and every privileged action must independently verify:

* Authentication
* Administrative role
* Required permission
* Target resource authorization
* Requested operation authorization

Client-side checks are not security boundaries.

Authorization must be enforced server-side.

Use deny-by-default behavior.

Any unknown, missing, invalid, expired, or insufficient authorization state must result in access denial.

Authorization failures must fail securely.

## Tenant / Account Isolation

This requirement is critical.

Normal users must never be able to access another user's:

* Profile
* Leads
* Contacts
* Research
* AI analysis
* Workflows
* Workflow executions
* Messages
* Outreach
* Campaigns
* Notifications
* Credits
* Subscription
* Payments
* API keys
* Developer Access settings
* Feedback
* Usage
* Activity
* History
* Files
* Exports
* Integrations
* Any other account-owned data

The Admin Dashboard is the intentional privileged exception.

Admin access must not weaken normal user isolation.

Cross-account data leakage must be impossible through:

* URL manipulation
* ID manipulation
* API requests
* Query parameters
* Request body manipulation
* Cached responses
* Search
* Pagination
* Filters
* Export endpoints
* Background jobs
* WebSocket/SSE events
* Server actions
* Internal APIs
* Direct object references

Every user-owned resource must resolve against the authenticated account/tenant context.

Do not rely on the frontend to enforce isolation.

## Admin Security

Protect the Admin Dashboard against:

* IDOR
* BOLA
* privilege escalation
* horizontal privilege escalation
* vertical privilege escalation
* session abuse
* unauthorized impersonation
* unauthorized data export
* unauthorized destructive operations
* CSRF where applicable
* XSS
* injection
* sensitive information disclosure
* accidental exposure of secrets
* insecure direct API access

Sensitive administrative operations must require appropriate confirmation and authorization.

Never expose:

* passwords
* password hashes
* authentication secrets
* API secret values
* payment secrets
* webhook secrets
* database credentials
* private encryption keys
* environment variables
* internal tokens

in the Admin UI, API responses, logs, exports, or error messages.

Do not invent architecture unnecessarily.

Do not create duplicate data sources unnecessarily.
