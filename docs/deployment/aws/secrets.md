# Secrets — Secrets Manager for the Full AcquisitionOS Variable Inventory

The authoritative variable list (per-variable: required/optional, secret/non-secret, where values come from) is [`../02-environment-variables-and-secrets.md`](../02-environment-variables-and-secrets.md). This page is the AWS mechanics: where each one lives, the exact commands, how the ECS task definition consumes them, and the IAM that makes it least-privilege.

**Golden rule (from the inventory):** anything without the `NEXT_PUBLIC_` prefix must never appear in client code, Git, or the image. In AWS terms: secrets go in **Secrets Manager** (or SSM Parameter Store) and are injected through the task definition's **`secrets`** section — never the plain `environment` block.

---

## 1. Two storage options

| | Secrets Manager | SSM Parameter Store (`SecureString`) |
| --- | --- | --- |
| Cost | ~per secret per month (free tier 30 days for new secrets) | effectively free |
| Features | rotation lambdas, cross-account, JSON multi-key | parameters, simple hierarchies |
| ECS support | `valueFrom` = secret ARN | `valueFrom` = parameter name/ARN |
| Recommendation | **Default in this handbook** | Fine budget alternative; same IAM pattern |

Either works with ECS. Commands below use Secrets Manager; SSM equivalents are noted inline.

## 3. Create / update / rotate commands

```bash
export PROJECT="acquisitionos"; export ENV_NAME="prod"

# Critical trio + extras (values: openssl rand -hex 32)
for S in JWT_SECRET ENCRYPTION_KEY CRON_SECRET; do
  aws secretsmanager create-secret --name ${PROJECT}/${ENV_NAME}/${S} \
    --secret-string "$(openssl rand -hex 32)"
done
# DB URLs (values from database.md §5 / RDS console)
aws secretsmanager create-secret --name ${PROJECT}/${ENV_NAME}/DATABASE_URL \
  --secret-string "postgresql://app_user:YOUR_DB_PASSWORD@DB_HOST:5432/acquisitionos?sslmode=require&connection_limit=10"
aws secretsmanager create-secret --name ${PROJECT}/${ENV_NAME}/DIRECT_URL \
  --secret-string "postgresql://app_user:YOUR_DB_PASSWORD@DB_HOST:5432/acquisitionos?sslmode=require"

# Any later-created provider key (repeat per name/value)
aws secretsmanager create-secret --name ${PROJECT}/${ENV_NAME}/STRIPE_SECRET_KEY \
  --secret-string "sk_live_YOUR_KEY"

# Update (new version — old versions are retained):
aws secretsmanager put-secret-value --secret-id ${PROJECT}/${ENV_NAME}/SMTP_PASSWORD \
  --secret-string "YOUR_NEW_APP_PASSWORD"

# Rotate = update + redeploy (see §5)
# SSM Parameter Store equivalents:
aws ssm put-parameter --name /${PROJECT}/${ENV_NAME}/JWT_SECRET \
  --type SecureString --value "$(openssl rand -hex 32)"
```

**Expected output:** `create-secret` returns JSON with the full ARN (note the random suffix — that is normal); `put-secret-value` returns `VersionId`. **Verify without printing values:** `aws secretsmanager describe-secret --secret-id ${PROJECT}/${ENV_NAME}/JWT_SECRET --query "VersionIdsToStages"` shows `["AWSCURRENT"]`.

Optional grouping alternative: one JSON secret with multiple keys (`{"SMTP_HOST":"...","SMTP_PASSWORD":"..."}`), referenced per variable in the task def as `arn:...:secret:name:jsonkey:SMTP_PASSWORD::`. Individual secrets are simpler to audit and rotate — that is the default here.

## 4. How the task definition consumes secrets

In `taskdef.json` (full file in [`manual-deployment.md`](./manual-deployment.md) §7), secrets are **not** `environment` entries — they live in the sibling **`secrets`** array:

```json
"secrets": [
  { "name": "DATABASE_URL", "valueFrom": "arn:aws:secretsmanager:us-east-1:YOUR_ACCOUNT_ID:secret:acquisitionos/prod/DATABASE_URL" },
  { "name": "JWT_SECRET",   "valueFrom": "arn:aws:secretsmanager:us-east-1:YOUR_ACCOUNT_ID:secret:acquisitionos/prod/JWT_SECRET" }
]
```

Mechanics: at **task launch** (not runtime re-read), the ECS agent fetches each value and injects it as a process env var — the app sees `process.env.JWT_SECRET` like any env var. Two roles are involved:

- **Execution role** (`acquisitionos-ecs-exec`): does the fetching. Needs `secretsmanager:GetSecretValue` (or `ssm:GetParameters`) on exactly your prefix, plus `kms:Decrypt` **only** if you use a customer-managed KMS key. It also needs ECR pull + log permissions (the AWS-managed `AmazonECSTaskExecutionRolePolicy` covers those).
- **Task role** (the app process at runtime): the app calls third-party APIs, not AWS ones — keep it empty/minimal. If you later adopt S3 for uploads, add `s3:PutObject` on that bucket to the task role, not the execution role.

## 5. IAM least-privilege examples

Execution-role inline policy (see creation in [`manual-deployment.md`](./manual-deployment.md) §7.2) — narrow by prefix, not `"Resource": "*"`:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["secretsmanager:GetSecretValue"],
    "Resource": "arn:aws:secretsmanager:us-east-1:YOUR_ACCOUNT_ID:secret:acquisitionos/prod/*"
  }]
}
```

SSM variant: `"Action": ["ssm:GetParameters"], "Resource": "arn:aws:ssm:us-east-1:YOUR_ACCOUNT_ID:parameter/acquisitionos/prod/*"`.

If secrets use a customer-managed CMK, add to the same role:

```json
{ "Effect": "Allow", "Action": ["kms:Decrypt"],
  "Resource": "arn:aws:kms:us-east-1:YOUR_ACCOUNT_ID:key/YOUR_CMK_ID" }
```

Human/CI access should be **describe/list** by default:

```json
{ "Effect": "Allow", "Action": ["secretsmanager:DescribeSecret", "secretsmanager:ListSecrets"],
  "Resource": "*" }
```

with `GetSecretValue` granted only to the execution role and to a small break-glass group. CI (Terraform apply) needs write (`CreateSecret`, `PutSecretValue`) on the prefix — assume the role via OIDC per [`terraform.md`](./terraform.md) §8, never static keys.

## 6. Rotation guidance (variable by variable)

| Secret | Rotation effect | Procedure |
| --- | --- | --- |
| `JWT_SECRET` | **Invalidates all sessions** (users must re-login; scheduled jobs unaffected) | Plan a window; `put-secret-value`; **redeploy the service** (tasks read secrets at launch — old tasks keep the old secret, so mixed-signing exists until all tasks cycle); verify logins. Only rotate on suspicion of leak or schedule |
| `DATABASE_URL` / DB password | App loses DB access until every task has the new URL | Rotate provider-side (`aws rds modify-db-instance --master-user-password` if master; or rotate `app_user` in psql), update secret, redeploy, verify `/api/health` |
| `CRON_SECRET` | EventBridge calls fail until the connection is updated too | Update the secret **and** the EventBridge connection auth, then redeploy |
| `STRIPE/RAZORPAY_WEBHOOK_SECRET` | Webhooks fail signature verification → **billing stops** | Re-register the webhook endpoint in the provider dashboard at the same time |
| Provider API keys (SMTP, Google, AI) | Feature-specific outage until redeploy | Update secret → redeploy → run the feature check |
| `NEXT_PUBLIC_APP_URL` | Build-time value | Not a secret; requires an image rebuild, not a redeploy |

Rule of thumb: **every secret change ends with an ECS service redeploy** (`aws ecs update-service --cluster acquisitionos-prod --service acquisitionos-app --force-new-deployment`), because values are injected at task start.

## 7. Handling rules (non-negotiable)

1. **Never commit secrets.** `.gitignore` already excludes `.env*`; keep it. Real values live only in Secrets Manager (or SSM), never in docs, issues, Slack, or `terraform.tfvars` for production (see [`terraform.md`](./terraform.md) §7).
2. **Never put secrets in the task def `environment` block** — `environment` values are visible in the task definition JSON and describe-task-definition output to anyone with ECS read access. The `secrets` array keeps values out of the definition entirely.
3. **Least privilege:** execution role reads only `acquisitionos/prod/*`; no `"Resource": "*"` on secret reads.
4. **Audit:** CloudTrail logs every `GetSecretValue` — check it if you suspect a leak.
5. **Verify without leaking:** prefer `describe-secret`/`wc -c` checks over printing values to terminals or CI logs.

## 8. Checklist

- [ ] Every SM-marked variable in §2 exists as `acquisitionos/prod/<NAME>` (or SSM path)
- [ ] ENV-marked variables are plain env entries; `NEXT_PUBLIC_APP_URL` baked at build time
- [ ] `AUTH_DEV_MODE` absent; no `localhost` anywhere in config
- [ ] Execution-role policy scoped to the secret prefix; task role minimal
- [ ] Task def uses `secrets`, not `environment`, for every secret
- [ ] Rotation runbook for `JWT_SECRET` and webhook secrets written down (§6) and tested once on staging
- [ ] `.gitignore` covers `.env*`; no secret in tfvars/CI logs/this documentation
